● Your three endpoints cover all three requirements. A few gaps would still
  cause trouble once you build it. The most important ones come first.

  1. Single filing lookup: route scope vs data source

  The requirement says "fetch a single filing by its accession number", with no
  company in it. Your route needs the ticker too, so a caller holding only an
  accession number can't use it.

  The catch is that EDGAR can't look a filing up by accession number alone:
  - The 10-digit prefix of an accession number is the filer's ID, which is often
    a filing agent rather than the company's CIK.
  - The archive path is sec.gov/Archives/edgar/data/{cik}/{accessionNoDashes}/,
    which needs the CIK.

  You have two options:
  - Keep the nested route. Ticker gives CIK, then you find the filing. This is
    cheap. Return 404 if the filing doesn't belong to that company.
  - Add GET api/filings/{accessionNumber}. This needs your own index (DB)
    mapping accession numbers to CIKs.

  Pick one on purpose and write down why.

  2. Pagination contract is missing

  - Add a limit (page size) parameter, with a default and a maximum.
  - Define the response envelope, e.g. { data: [...], nextCursor: string | null 
    }.
  - Make the sort stable: filingDate desc, then accessionNumber desc to break
    ties. Without the tie-breaker, the cursor can skip or repeat rows.
  - Tie the cursor to its filters. Either encode the filters inside the cursor,
    or reject a cursor sent with different filters.

  3. Filter semantics are undefined

  - Which date does the range apply to? Filing date or report date? The
    requirement doesn't say, so choose one (filing date is the likely one) and
    document it.
  - Are the bounds inclusive? Use ISO YYYY-MM-DD. Return 400 when start > end.
  - Form type:
    - Can callers pass more than one? 10-K,10-Q or a repeated param.
    - What about amendments? Does 10-K also match 10-K/A? Decide.
    - Matching should be case-insensitive.

  4. Response shapes are undefined

  Company: at minimum cik, ticker, name. Optional: exchange, sic.

  Filing: accessionNumber, formType, filingDate, reportDate (nullable, since
  some forms have none), primaryDocumentUrl.
  - The URL is built as https://www.sec.gov/Archives/edgar/data/{cik}/{accession
    NoDashes}/{primaryDocument}, so the CIK is needed internally.
  - Pick one accession format, dashed (0000320193-24-000123) or not, and accept
    both as input.

  5. Ticker handling

  - Make it case-insensitive.
  - Normalize share-class tickers: BRK.B, BRK-B and BRKB should resolve the same
    way.
  - Source: sec.gov/files/company_tickers.json. Cache it and refresh it daily.

  6. EDGAR upstream realities

  - data.sec.gov/submissions/CIK##########.json only holds the most recent ~1000
    filings. Older ones are in extra files listed under filings.files.
    Paginating past that limit means fetching those files.
  - SEC requires a User-Agent header with contact info and allows at most 10 
    requests per second. You need caching and request throttling on the outbound
    side.

  7. Error contract

  ┌─────────────────────────────────────┬───────────┐
  │                Case                 │  Status   │
  ├─────────────────────────────────────┼───────────┤
  │ Unknown ticker, or filing not found │ 404       │
  ├─────────────────────────────────────┼───────────┤
  │ Bad date, bad cursor or bad limit   │ 400       │
  ├─────────────────────────────────────┼───────────┤
  │ SEC down or slow                    │ 502 / 503 │
  ├─────────────────────────────────────┼───────────┤
  │ Rate limited                        │ 429       │
  └─────────────────────────────────────┴───────────┘

  Use one consistent error body for all of them.

  8. Naming consistency

  - filing (singular) vs filings: use plural for both, so
    .../filings/{accessionNumber}.
  - Use plural companies.
  - Add a version prefix: api/v1.
  - Query params: your form-type uses kebab-case. Pick one convention (kebab or
    camelCase) and use it everywhere.

  Revised sketch

  GET /api/v1/companies/{ticker}
  GET /api/v1/companies/{ticker}/filings?formType=10-K,8-K&startDate=2024-01-01&
  endDate=2024-12-31&limit=50&cursor=...
  GET /api/v1/companies/{ticker}/filings/{accessionNumber}
  GET /api/v1/filings/{accessionNumber}        # optional, needs own 
  accession→CIK index

  The requirements don't need these, but they're cheap in Nest: @nestjs/swagger
  for API docs, Zod validation through StandardSchemaValidationPipe,
  @nestjs/cache-manager for caching, and @nestjs/resilience for retries against
  SEC.

  The decisions only you can make are #1 (whether to add a global accession
  route) and #3 (which date the range filters on, and whether amendments match).

● No. None of the data we return mentions a quarter. Each filing has five
  fields:

  accessionNumber, formType, filingDate, reportDate, primaryDocumentUrl

  - filingDate is the date the filing was submitted to SEC.
  - reportDate is the last day of the period the report covers, e.g. 2025-09-27
    for Apple's FY2025 10-K. This is the field consumers should compare on.
  - accessionNumber looks like it might hold a date, but it doesn't contain a
    quarter. Its format is {filer ID}-{2-digit year}-{sequence}, e.g.
    0000320193-25-000079. The 25 is the calendar year SEC received the filing,
    and the 10-digit prefix is often a filing agent rather than the company.
    It's an ID, not something to read dates from.

  What you heard is right. Fiscal quarters don't line up across companies:
  - Apple's fiscal year ends in late September, so its "Q1" is roughly October

❯ Wonderful. Then let's the next step for the API - a cache layer. We don't     
  want to hit the upstream every time someone requests data. In-memory cache is 
  enough but I want your help in deciding where to put the cache layer, list    
  pros and cons of putting it inside each of our existing services or the       
  controller itself and let me decide which one to go with.                     

● The best spot is the edgar service, just before requests reach SEC, so a cache
  hit never touches SEC or the rate limiter. Each option below is compared
  against the two calls we make to SEC:

  - Ticker list: fetched by getCompanyTickers() and used by every endpoint. It's
    already cached for 24h inside TickerCikService.
  - Company filings: fetched by getSubmissions(cik). Both filing endpoints call
    it with the same CIK, and only filter the result differently afterwards.

  1. Controller (cache the HTTP response, e.g. Nest's CacheInterceptor)

  Pros
  - Least code. Nest has a built-in interceptor for this
    (@nestjs/cache-manager).
  - A hit skips everything, including filtering and wrapping.

  Cons
  - The cache key is the full URL. ?form-type=10-K, ?form-type=10-k and
    ?form-type=8-K,10-K are all separate entries for the same SEC data, so a new
    filter combination still hits SEC.
  - The list endpoint and the single-filing endpoint can't share cached data.
  - The response wrapper and errors make this harder. Error responses must not
    be cached, and that takes extra care with the error filter.
  - Caching becomes an HTTP concern instead of a data concern.

  2. CompaniesService

  Pros
  - Knows the domain: it can cache the converted filings per CIK and filter them
    afterwards.
  - Both filing endpoints share one entry per company.

  Cons
  - Mixes caching into business logic, which goes against the separation of
    concerns you asked for.
  - The ticker list is still cached separately in TickerCikService, so there'd
    be two caching mechanisms in two places.
  - Any future code that calls EdgarService directly gets no cache.

  3. TickerCikService (extend what's there)

  Pros
  - A cache already exists there: 24h, and concurrent requests share one load.

  Cons
  - It only resolves ticker to CIK. Filings don't go through it, so it can't
    cache them without taking on a second job.

  4. EdgarService (cache raw SEC responses, keyed by URL or CIK)

  Pros
  - One place for both SEC calls. Every endpoint, filter combination and future
    caller benefits.
  - The key is small and predictable: one entry per company plus one for the
    ticker list. Filters don't multiply entries.
  - A hit returns before the rate limiter, so it uses no SEC capacity.
  - TickerCikService could drop its own cache and become a simple lookup.
  - Easy to keep errors out: only successful responses get stored.

  Cons
  - EdgarService now does two jobs: talking to SEC and caching.
  - The cache holds raw SEC data, so every hit still filters and converts.
    That's cheap: about 1000 rows in memory.
  - The full submissions file is the largest thing we store. The recent section
    alone is about 1000 filings, roughly 0.5–1 MB per company. You need a limit
    on entries or an eviction rule.

  5. Separate caching wrapper around EdgarService

  This keeps all of option 4's benefits but puts caching in its own class, the
  same way the rate limiter is its own class. Controllers and services call the
  cached version, which calls the real EdgarService on a miss.

  Pros
  - Same benefits as option 4.
  - Each class has one job: talking to SEC, rate limiting, caching. That matches
    the structure you set up.
  - Caching can be tested on its own with a fake EdgarService.

  Cons
  - One more class, plus some wiring so callers get the cached version.

  Decisions for any option

  - How long to keep data: about 24h for the ticker list. For filings, roughly
    5–15 minutes is a reasonable trade-off, since companies file throughout the
    day.
  - Never cache errors.
  - Share in-flight requests: when several requests for the same company arrive
    at once, make one SEC call. Without this, the cache misses that happen while
    a request is in flight all go to SEC.
  - Memory limit: cap the number of companies held and evict the least recently
    used.

  Recommendation: option 5, or option 4 if you don't want the extra class.
  Options 1 and 2 cache at the wrong level for how our data is shaped.

  Which one do you want?

● I recommend cursor-based paging. Performance isn't the reason, though: with
  our data, the three styles perform the same. The real differences are what
  consumers see when new filings arrive mid-iteration, and what happens once we
  page past the ~1000 recent filings.

  Why performance doesn't decide it

  The usual reason to prefer cursor paging is database cost: OFFSET 50000 makes
  the database scan and throw away 50,000 rows, while a cursor seeks straight to
  an index position. We don't have a database. A company's ~1000 recent filings
  are already in memory (cached), and every request filters and sorts them
  anyway, so taking a page out of the result costs the same whichever style we
  use.

  The three options

  Cursor (?limit=50&cursor=<opaque>). The cursor encodes where the last page
  ended, i.e. the last (filingDate, accessionNumber) returned. Together those
  two values identify a filing uniquely.

  Pros:
  - Stable while data changes. New filings appear at the top, since the list is
    newest first. A cursor continues from a specific filing, so a consumer
    partway through never sees duplicates or gaps. This matters because cached
    filings refresh every 10 minutes, and a long-running sync can span a
    refresh.
  - Works past the recent filings. SEC splits older filings into extra files,
    each labelled with a filing date range. A cursor holding a date tells us
    which file to read next. With offsets and a form-type filter, finding "item
    500" means reading and filtering every earlier file first.
  - Matches how software reads lists: follow nextCursor until it's null. Clients
    need no page arithmetic.

  Cons:
  - No jumping to page N, and no fetching pages in parallel (each page needs the
    previous page's cursor).
  - The token must be encoded and checked: a bad cursor gives a 400. You also
    have to decide what happens when a cursor is sent with different filters.
  - Slightly harder to try out by hand, because the cursor is an opaque string.

  Offset + limit (?offset=100&limit=50).

  Pros:
  - Simple and transparent. Clients can fetch pages in parallel or jump
    anywhere.
  - Easy to implement on in-memory data: one slice.

  Cons:
  - Data changes cause duplicates. If 2 new filings arrive mid-sync, every later
    position moves down by 2, so the next page repeats 2 already-seen filings.
    Gaps would need deletions, which SEC rarely does. Machine consumers can drop
    duplicates by accession number, but every client has to know to do that.
  - Doesn't work well past the recent filings combined with filters (see above).

  Page + size (?page=3&size=50).
  This is offset + limit with page-number arithmetic. It has the same pros and
  cons, plus one more con: it's less flexible. Changing size partway through
  misaligns the pages. Page numbers mainly suit human-facing interfaces ("page 3
  of 12"), which isn't your audience.

  Summary

  ┌───────────────────────────┬─────────┬─────────────────┬─────────────────┐
  │                           │ Cursor  │ Offset + limit  │   Page + size   │
  ├───────────────────────────┼─────────┼─────────────────┼─────────────────┤
  │ Speed on our data         │ Same    │ Same            │ Same            │
  ├───────────────────────────┼─────────┼─────────────────┼─────────────────┤
  │ New filings mid-sync      │ Stable  │ Duplicates      │ Duplicates      │
  ├───────────────────────────┼─────────┼─────────────────┼─────────────────┤
  │ Paging past the recent    │ Natural │ Hard with       │ Hard with       │
  │ filings                   │         │ filters         │ filters         │
  ├───────────────────────────┼─────────┼─────────────────┼─────────────────┤
  │ Jump or parallel fetch    │ No      │ Yes             │ Yes             │
  ├───────────────────────────┼─────────┼─────────────────┼─────────────────┤
  │ Fit for machine consumers │ Best    │ Good            │ Weakest         │
  └───────────────────────────┴─────────┴─────────────────┴─────────────────┘

● These are the other approaches worth considering, plus an updated
  recommendation. (My previous reply was also cut off mid-sentence; the open

  Other approaches

  4. Transparent cursor: "items after this ID" 
  (?limit=50&after=0000320193-24-000123)
  This is what Stripe does (starting_after=<id>). It works like a cursor, but
  the position is a readable accession number instead of an opaque token.
  - Pros:
    - Same stability as an opaque cursor: new filings don't shift anything.
    - No encoding and no checking of a token, so it's easy to debug and try out
      by hand.
    - Clients can build it themselves from the last item they received.
  - Cons:
    - We have to find that accession number to know where to continue. That's
      trivial in memory. Past the recent filings it's awkward, because finding
      which older SEC file holds it needs the filing date, and the accession
      number only contains the year.
    - Clients can't tell whether we sort by filing date, report date or
      accession number. With an opaque cursor that detail stays hidden.
    - If the referenced filing ever disappears (very rare at SEC), the position
      is lost and we have to return a 400.

  5. Date-window paging (client narrows start-date/end-date itself)
  There's no paging feature; clients use the date filters we already have.
  - Pros: nothing to build, and no state on either side.
  - Cons:
    - Page sizes are uneven.
    - Our date filter is on report date but the sort is on filing date, so the
      windows don't line up with the order clients see.
    - Every client has to write its own loop.

  Not a fit on its own.

  6. Snapshot paging (the server keeps the result set; Elasticsearch scroll / 
  point-in-time style)
  The first request freezes the result and gets a snapshot ID, and later pages
  read from that frozen copy.
  - Pros: perfectly consistent, even when cached data refreshes mid-sync.
  - Cons:
    - State on the server: memory, expiry and cleanup.
    - Breaks with several instances unless the snapshots are shared.
    - Much more work than the problem calls for: cursors already handle new
      filings at the top, and SEC rarely edits or deletes filings.

  Overkill here.

  7. "Changes since" sync (?filed-since=2024-05-01)
  This isn't paging; it's a way to skip it. Clients that keep a local copy fetch
  only what's new since their last run.
  - Pros: the most efficient pattern for software that keeps a copy of the data.
    After the first full read, each sync is tiny.
  - Cons: it adds to paging rather than replacing it, since the first full read
    still needs paging. It also needs a filing-date filter; today we only filter
    on report date.

  Worth adding later.

  Ways to send the next-page position (they work with any style above)
  - A next URL in the response body: a ready-to-call URL that clients just
    follow. This fits machine consumers best: it needs no URL building, and it
    keeps the filters and limit consistent between pages automatically.
  - Link: <…>; rel="next" header (RFC 8288): the same idea in a standard HTTP
    header, which some HTTP clients and SDK generators follow automatically.
    It's less visible than a body field.
  - Range: items=0-49 header: rare, and few tools support it. Skip.

  - Rejected cursors get a 400 that says why:
    - A changed filter: "cursor does not match the current filters (form-type,
      start-date, end-date); repeat the filters used for the first page, or
      start again without a cursor".
    - A malformed cursor: "cursor is invalid; pass the nextCursor value from a
      previous response unchanged". It is rejected before any SEC request.
  - The same filters written differently, such as 10-k,10-Q vs 10-Q,10-K, are
    accepted.
  - limit can change between pages, since it isn't a filter.
  - The cursor stores the last filing returned and the filters that produced it.
    A page continues after that position, so filings that arrive between
    requests cause no duplicates or gaps. This still works if the cursor's
    filing has disappeared.
